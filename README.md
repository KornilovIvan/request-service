# request-service

HTTP-сервис заявок. Хранит клиентов, заявки, документы к заявкам и справочник статусов. Данные лежат в PostgreSQL.

Стек: Go 1.26.6, [Gin](https://github.com/gin-gonic/gin) 1.10.0, `database/sql` с драйвером [pgx](https://github.com/jackc/pgx) 5.7.2, PostgreSQL 16.

## Что умеет

- Создаёт клиента и отдаёт одного клиента или весь список.
- Создаёт заявку от имени клиента, отдаёт карточку и список.
- Меняет статус заявки. При переводе в `closed` проставляет `closed_at`, при любом другом статусе сбрасывает его в `null`.
- Прикладывает документ к заявке и отдаёт документ по id или список документов заявки.
- Отдаёт три статуса, которые миграция записывает в базу: `active` («В работе»), `pending` («Ожидает»), `closed` («Закрыта»).

Список заявок можно сузить query-параметрами `status`, `created_from` и `limit`. В каждой заявке списка и карточки есть имя клиента (`customer_name`): оно берётся одним `JOIN`, отдельного запроса на каждую строку нет. Клиент без заявок в этот список не попадает.

Тело ошибки всегда одно и то же: `{"error":"..."}`. Текст фиксированный, в ответ не попадает сообщение драйвера PostgreSQL. Пустой список — это `[]`, не `null`.

## Слои

Запрос проходит три слоя. Каждый делает свою работу и не залезает в чужую.

| Слой | Пакет | Что делает |
| --- | --- | --- |
| HTTP | `internal/handler` | Читает путь, query и JSON, выбирает код ответа |
| Правила | `internal/service` | Проверяет имя, заголовок, статус, дату и limit |
| База | `internal/repository` | Пишет SQL и сканирует строки |

Сервис не импортирует Gin. Репозиторий не импортирует Gin. Обработчик не пишет SQL. Общие структуры ответа лежат в `internal/model`. Сборку роутера делает `handler.NewRouter`: её вызывает и `cmd/app`, и HTTP-тесты.

`cmd/app/main.go` читает `DATABASE_URL` и `HTTP_ADDR`, открывает пул подключений, проверяет его через `Ping` и запускает роутер. Файл `.env` процесс сам не читает: переменные должны уже быть в окружении.

## Данные

Миграции в `migrations/`. Их применяет [golang-migrate](https://github.com/golang-migrate/migrate).

| Таблица | Содержимое |
| --- | --- |
| `customers` | Клиент: `id`, `name`, `created_at` |
| `statuses` | Код и название статуса. Три строки создаёт миграция |
| `requests` | Заявка: клиент, заголовок, статус, `created_at`, `closed_at` |
| `documents` | Документ заявки: `request_id`, `name`, `created_at` |

`id` — `integer GENERATED BY DEFAULT AS IDENTITY`. Внешние ключи: заявка ссылается на клиента и на код статуса, документ ссылается на заявку. Сервис проверяет клиента и статус до вставки и отвечает своими текстами; ключ в базе не даёт записать строку, которая ссылается в пустоту.

## Запуск рядом с Postgres в Docker

Нужны Docker и Go 1.26.6.

```bash
make up
make migrate-up
export DATABASE_URL=postgres://requests:requests@localhost:5432/requests?sslmode=disable
export HTTP_ADDR=:8080
go run ./cmd/app
```

`make up` поднимает только Postgres (`postgres:16-alpine`) на порту `5432`, пользователь и база — `requests` / `requests`. `make migrate-up` прогоняет все `*.up.sql` внутри сети Compose. С хоста хост базы — `localhost`, не `postgres`: имя `postgres` резолвится только между контейнерами.

Проверка:

```bash
curl -s localhost:8080/health
```

Ответ: `{"status":"ok"}`.

Остановить контейнеры: `make down`.

Те же переменные лежат в `.env.example`. Каталог `.env` в git не входит.

## Запуск самого приложения в контейнере

`Dockerfile` собирает бинарник `./cmd/app` в образе `golang:1.26.6-alpine` и копирует его в `alpine:3.20`. Сервис `app` в `docker-compose.yml` слушает `8080` и ходит в Postgres по адресу `postgres:5432`.

Схема сама при старте контейнера не накатывается. Сначала миграции, потом приложение:

```bash
make up
make migrate-up
docker compose up --build app
```

## Миграции и тесты

| Команда | Действие |
| --- | --- |
| `make migrate-up` | Применить миграции к базе `requests` |
| `make migrate-down` | Откатить все миграции этой базы |
| `make test-db` | Создать `requests_test`, если её нет, и накатить миграции туда |
| `make test` | Подготовить `requests_test` и запустить `go test ./...` |
| `make lint` | `go vet ./...` |

`make test` подставляет `TEST_DATABASE_URL` на `localhost` и базу `requests_test`. Тесты сами миграции не применяют. Перед каждым HTTP-тестом `internal/testdb` очищает `documents`, `requests` и `customers` и не трогает `statuses`. Роутер поднимается через `httptest.NewServer`, репозиторий не подменяется моком. База `requests` этими тестами не чистится.

## API

Базовый путь: `http://localhost:8080`. Успешное создание — `201`, чтение и смена статуса — `200`. Неизвестный id в пути — `404`. Неверное тело или query — `400`. Сбой базы — `500` и текст `internal error`.

### Клиенты

`POST /api/v1/customers`

```bash
curl -s -X POST localhost:8080/api/v1/customers \
  -H 'Content-Type: application/json' \
  -d '{"name":"Альфа"}'
```

Имя обрезается по краям. Пустое имя или имя из пробелов — `400`, `name is required`.

`GET /api/v1/customers` — список, новые сверху.

`GET /api/v1/customers/1` — один клиент. Нечисловой или неположительный id — `400`, `invalid id`. Нет такого клиента — `404`, `customer not found`.

### Статусы

`GET /api/v1/statuses` — три объекта в порядке кода: `active`, `closed`, `pending`.

### Заявки

`POST /api/v1/requests`

```bash
curl -s -X POST localhost:8080/api/v1/requests \
  -H 'Content-Type: application/json' \
  -d '{"customer_id":1,"title":"Подключить отчёт","status":"active"}'
```

Заголовок обрезается по краям. Пустой заголовок — `400`, `title is required`. Статус не из трёх кодов — `400`, `invalid status`. Клиента с таким `customer_id` нет — `400`, `customer not found` (id пришёл в теле, поэтому это не `404`).

В ответе карточка:

```json
{
  "id": 1,
  "customer_id": 1,
  "customer_name": "Альфа",
  "title": "Подключить отчёт",
  "status": "active",
  "created_at": "2026-11-01T20:00:00Z",
  "closed_at": null
}
```

`GET /api/v1/requests/1` — та же карточка. Нет заявки — `404`, `request not found`.

`PATCH /api/v1/requests/1/status`

```bash
curl -s -X PATCH localhost:8080/api/v1/requests/1/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"closed"}'
```

Неизвестный статус — `400`, `invalid status`. Нет заявки — `404`, `request not found`. После `closed` поле `closed_at` заполнено.

`GET /api/v1/requests` — список по `created_at` по убыванию.

| Параметр | Правило |
| --- | --- |
| `status` | `active`, `pending` или `closed`. Ключ без значения (`?status=`) фильтр не включает и ошибкой не считается. Другое значение — `400`, `invalid status` |
| `created_from` | День `YYYY-MM-DD`. В выборку попадают заявки с `created_at` не раньше полуночи этого дня по UTC. Дата позже сегодняшнего дня UTC или неразборчивая дата — `400`, `invalid date` |
| `limit` | Целое от 1 до 100. Если параметра нет, берётся 20. `0`, `101` или нечисло — `400`, `invalid limit` |

Пример: заявки в работе с 1 января 2022 года, не больше 20 штук.

```bash
curl -s 'localhost:8080/api/v1/requests?status=active&created_from=2022-01-01&limit=20'
```

### Документы

`POST /api/v1/requests/1/documents`

```bash
curl -s -X POST localhost:8080/api/v1/requests/1/documents \
  -H 'Content-Type: application/json' \
  -d '{"name":"Договор.pdf"}'
```

Пустое имя или имя из пробелов — `400`, `document name is required`. Нет заявки — `404`, `request not found`.

`GET /api/v1/requests/1/documents` — документы этой заявки, новые сверху. Нет заявки — `404`, `request not found`.

`GET /api/v1/documents/1` — один документ. Нет документа — `404`, `document not found`.

## Каталоги

```text
cmd/app/            точка входа
internal/handler/   маршруты и коды ответов
internal/service/   проверки
internal/repository/ SQL
internal/model/     структуры JSON
internal/testdb/    подключение к requests_test и очистка таблиц
migrations/         схема
```
